本页保留已提交版本的详细规则。历史验收日期是检查安排，不代表验收已经完成；实际运行以本地证据为准。

## 自动发送时间与内容

以下均为北京时间（`Asia/Shanghai`），需本地启用相应功能；不是每次采集都发消息。

| 时间或触发条件 | 文字 | 图片 | Excel |
| --- | --- | --- | --- |
| 每天10:00日报 | 简短日期提示，真实@投手一次 | 每日三件事导读图在首位，随后昨日利润图（可能多页）、两日消耗对比图、四宫格贡献占比图 | 昨日逐计划利润明细 |
| 每个偶数整点：00:00、02:00…22:00 | 10:00、12:00、14:00、16:00、18:00卡片内真实@投手；其他时段正常不@ | 余额、估算可用时长，以及本两小时/前两小时/昨日同段速率对比 | 无 |
| 余额不高于500元时 | 简短低余额预警，真实@投手；同一预警状态去重 | 非定时时点用文字卡片，定时时点可合并到余额图 | 无 |
| 半小时监测发现符合提醒条件的异常时 | 具体计划、指标变化、退款提示或数据缺失；文字卡片 | 无独立图片 | 无 |
| 持续采集/服务故障或恢复时 | 故障、数据缺口、日报延迟或恢复说明；文字卡片 | 无独立图片 | 无 |

**凌晨不再单独发送两日对比图或四宫格。** 两张图只随10:00日报发送，使用前两个完整自然日（D−2、D−1）；00:00只保留正常余额提醒（不@投手）及按条件触发的异常提醒（保留@）。10:00余额提醒与日报用途不同，仍各自保留。

日报重试窗口为10:00（含）至12:00（不含），已确认发送的部分不重复发送；结果未知时先核实。小时采集只采集，日报解读和指定日期日报仅在用户请求时回复，不额外定时发送。反馈继续暂停，不自动调整预算、ROI或计划状态。

详细发送、去重和缺失处理见[自动日报与提醒规则](automatic-profit-daily.md#现行自动发送清单)。

## 群历史权限与发送后查重

机器人以应用身份读取群历史，除基础消息读取权限外，还需开通 **`im:message.group_msg`（获取群组中所有消息）**。在飞书开发者后台的现有应用中申请该权限，并完成版本发布及所需管理员审批；以实际群历史接口成功返回为生效依据，不以页面勾选代替验证。无需改用个人账号授权。[官方接口说明](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/list)

验收只回读：完整分页获取目标时段群历史，与事件账本、发送回执和日志核对正文、图片与Excel，记录查询起止时间及分页完整性。不同消息ID或重新上传的相同附件也可能重复，不能只查单个回执。权限失败或历史不完整时明确查重边界，不宣称全群通过。

日报整包只真实@投手一次；10点独立余额提醒的合法@另计。常规余额提醒只在10、12、14、16、18点@投手，20点等其他时段无异常不@；异常按原规则核对。退款提示按计划、指标与实际快照区间查重，不把不同区间的新提醒误判为重复。姓名文字不算原生@。

沿用已安排的验收任务，不额外发测试消息、不主动重发、不清空账本。完整规则见[群历史权限与重复发送核验](automatic-profit-daily.md#群历史权限与重复发送核验)。证据只留本地，反馈继续暂停，不自动调整预算、ROI或计划状态。

## 日报发送顺序与统一口径

每天10:00沿用同一个日报任务，按以下顺序发送：

1. 简短日期提示，**真实@现有配置投手一次**。
2. **每日三件事导读图**：昨日结果、相比前日的变化、今天需要人工核查的三件事，替代长文字摘要。
3. 原利润图，保留全部分页。
4. 昨日逐计划利润明细Excel。
5. 两日广告消耗对比图。
6. 两日贡献占比四宫格。

导读不另发，不再次@。原利润图与Excel使用昨日（D−1）数据，两日图使用前两个完整自然日（D−2、D−1）；时间统一为北京时间。10:00独立余额提醒按原规则运行，其@不计作日报重复@。

| 展示分类 | 归类规则 | 利润与广告费如何展示 |
| --- | --- | --- |
| 已关联商品 | 计划能明确关联到商品 | 同商品汇总；正利润商品进入盈利贡献饼图，亏损商品及金额单列 |
| 全店托管 | 仅含计划信息明确标注“全店托管”的计划 | 广告费与预估利润单列，与原计划明细对应；不进入商品盈利贡献分母 |
| 其他未关联计划 | 多商品或未能明确关联商品的其他计划 | 广告费标“商品归属待核验”，利润单列“其他未关联计划利润”；不混入全店托管，不强行分摊，不进入商品盈利贡献分母 |

**商品归属未知，不等于计划金额未知。** 有证据的计划广告费和可计算利润照常保留；缺少GMV、消耗或成本口径等计算依据时，相应金额标“待核验”，不能补0。

导读、利润图、Excel和两日图按同账户、同日期核对，不能将一个计划与多个计划的合计使用同一名称。已关联商品的正利润、负利润，加上全店托管及其他未关联计划的利润，应还原相同覆盖范围的可计算利润合计；该合计不代表完整账户最终财务利润。缺失计划数量采用同份日报范围，包含直播缺口。

导读前日优先读取已完成新版日报账本；旧账本情况下，只接受同账户、准确日期、唯一一份完整发送回执且金额复核通过的新版报表。缺失、版本有歧义或政策不同，比较标待核验，不借用其他日期数据。两日小时明细与对应日报不一致时，同样标待核验。

已冻结或已发送的日报不重排、不补发；新口径用于新生成报表。继续暂停反馈，不自动调整预算、ROI或计划状态。生产配置、真实报表、群聊及人员身份、发送回执只留本地，不上传仓库。

## 发送前自动对账

每份新日报在第一条提示、上传图片或Excel之前先做整包体检，重试也重新检查。复算计划利润与合计，核对接口汇总、导读日期与核查事项、全店托管和未关联分类、两日图数据、Excel保存数值，以及附件顺序和哈希。

- **金额、日期、账户、计算口径或分类相互矛盾：阻止发送。** 不自动修改金额、清账本或重发来绕过问题。
- **只是缺少数据：保留“待核验”。** 不补0，不把部分利润说成完整账户利润；文件缺失或无法核验则不能发送。
- 体检结果只写本次输出目录的`preflight.json`和`preflight.txt`，不添加群消息或附件，不增加@。
- 图片通过确定性生成输入与文件哈希绑定检查；第一期不做图片OCR，也不代表退款和费用已经完成财务核实。

配置、数据、历史回执保持；反馈继续暂停，不自动调整预算、ROI或计划状态。

## 第一期数据完整性看板

本地`preflight.json`的`coverage`与`preflight.txt`记录本次报表计划总数、可测算/利润待核验数量和比例、缺GMV/广告消耗/利润的数量、已知零消耗数量、商品归属分类、数据截止时间及逐计划缺口。缺失字段计数可以重叠，不能相加冒充缺失计划数。报表内可测算比例不代表全账户覆盖率；全账户覆盖率无独立证据时为待核验，空计划清单也不能当作零消耗或零利润。

商品归属来自同账户同日期两日图保存的映射证据，分已关联、明确全店托管、其他未关联与映射证据待核验；没有映射证据不得直接判为未关联。商品归属未知不等于金额未知，不因此抹去已知金额。已知零广告消耗默认不推断GMV；唯一例外为下述经确认的“零消耗GMV业务补值规则”。缺失用null与待核验表示，保留原模型政策，不推断实际退款、成本或最终财务利润。

新生成日报导读在“昨日结果”内用一句话说明“本次报表共N个计划，X个可测算、Y个利润待核验；非全账户最终利润”。该句与本地体检单从同份输入计算并核对，矛盾阻止发送。既有冻结包保持原导读结构，不重排或重发；本地体检可增加覆盖汇总。完整看板不作为群消息或附件发送，不增加发送条数或@，不改变原图表及Excel顺序。

真实看板、逐计划缺口和验收样稿仅保存在本地。仓库测试使用虚构数据；保留配置、数据、发送账本、反馈暂停和dry_run，不自动调整预算、ROI或计划状态。


## 零消耗GMV业务补值规则（已确认）

仅商品计划（VIDEO_PROM_GOODS）满足以下全部条件时，将缺失GMV按0参与模型计算：同账户、同自然日完整分页的官方无消耗筛选证据确认消耗为0；首次GMV缺失后，按计划ID、相同日期再查询一次官方计划报表；复查成功且分页完整，GMV仍未返回。批量复查按场景和接口限制分组；出现日期、计划范围或消耗矛盾即阻止继续计算。权限失败、超时、分页缺失、无请求证据、消耗未知及直播计划均不得补值。

这是用户确认的业务估算规则，不是平台确认“零消耗必然零成交”。保留`raw_gmv=null`、零消耗证据、复查日期和请求流水；补值行记录`gmv_source=business_rule_zero_spend`及规则版本，标注“业务规则补值”。接口已有GMV（包括真实0或正值）优先，绝不覆盖；后续收到真实值时，新生成报表采用真实值，原冻结包不改写。

导读与本地体检区分可测算数、业务补值数、原始GMV缺失数及剩余待核验数。Excel明细状态及“缺失与对账”页明确标注补值；模型利润随GMV=0计算，但不宣称为已核实经营利润。利润图不为业务补零计划新增零柱分页，注明数量并引导查看Excel，不增加发送消息和@。其他原图表与Excel发送顺序保持，直播仍待核验。

发送前对账核验补值资格与证据，补值不能冒充独立API对账结果；原始API无记录仍保留该事实。仅对新生成报表生效，不重发历史日报。反馈暂停、dry_run和人工投放边界不变，不调整预算、ROI或计划状态。真实数据、配置、身份及回执仅留本地，GitHub只提交脱敏代码、规则和虚构测试。

## 待核验跟踪与业务补值对照（一期）

原日报引擎在当日日报已完成发送后，在既有补发窗口内执行一次本地跟踪；不新增定时任务、独立消息、附件或@。结果保存在本地`data/qianchuan/verification_tracker.db`及`out/verification_tracker/<账户>/<核验日期>/tracker.json`、`tracker.md`，不进入GitHub。首次部署可手动只读运行一次验证，不触发日报发送。

只自动登记发送账本已完成、回执完整、文件哈希和金额复核通过的新版日报。按账户、数据日、原报表哈希、计划记录版本，重复登记与同日重复运行不增加重复记录。缺GMV、消耗、利润、业务补值与历史商品归属缺证据分别保留；同计划不同报表版本不能混成同一基线。原报表、冻结包及发送回执不修改。

商品金额每日按原场景、原日期与计划ID查询最近7个完整自然日，完整分页并保留请求证据。空记录、缺字段、超时、权限失败或范围冲突均保留待核验，不补0，不把业务补值当作问题已解决；每日失败记录后等下一日复查，不额外发故障消息。更早记录仍保留并标待人工核验。直播缺单计划维度、历史商品映射缺证据时说明原因，不用当前映射冒充历史证据。

取得同日真实GMV和广告消耗后，按原报表保存的退款率、采购倍率及费用政策重算模型利润，记录原始值、新值、GMV差额、消耗差额、利润差额和核验时间。只有完整证据才能关闭金额缺口；原利润未知时利润差额也待核验。商品归属仍缺证据时，金额可核验完成，但整项保持待人工核验。已关闭金额项一期不继续监测后续归因修订；这不是最终财务利润认证。

本地看板包含状态、具体原因、检查次数/API查询次数和历次观察。一个实际批次请求可覆盖多个计划，计划检查次数不等于接口调用次数。原始版本和观察保留，重启后可恢复；异常仅写本地，不影响日报发送或诱发重发。继续暂停投手反馈，保留dry_run，不调整预算、ROI或计划状态。

### 粗略模型：投放重点、异常合并与一问即答

- 日报首图增加盈利、亏损、广告消耗三个关注排序，每类最多三项。不增加独立消息或重复 @。这是人工关注顺序，不是加预算指令，不做周报或新增精细金额核对。
- 有同日同账户商品关联证据的计划按商品汇总；全店托管单列；未关联计划分别展示。某指标缺失时不参加该指标排名，业务规则补值仍注明。
- 同类型、同快照区间的新规则异常合成短卡，每张最多八个计划；保留原事件、冷却期和准入检查。退款提示和资金预警不混入规则异常。
- 可以问“昨天哪个商品赚得最多”“昨天哪个亏损最多”“昨天广告费花在哪里”。直接读取北京时间对应完整自然日的已完成新版日报，最多列三项；缺日报则待核验，不用旧日期替代，不调用大模型猜数。没有商品映射时明确按计划展示。
- 已发历史报表不重写；反馈继续暂停；不自动调整预算、ROI 或计划状态。

### 异常提醒ROI显示

已知ROI统一显示两位小数（如 `0E+2` 显示为 `0.00`），缺失仍显示“暂无”。此修复仅影响新提醒的文字显示，不改计算和异常阈值，不重发历史消息。详见[ROI显示规则](current-profit-rules.md#异常提醒roi显示规则)。反馈继续暂停，不自动调整投放。
